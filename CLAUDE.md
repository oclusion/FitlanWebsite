# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev       # Vite dev server
npm run build     # production build to dist/
npm run preview   # serve the dist/ build locally
npm run lint      # oxlint (not eslint)
npm start         # node server.js — production process (Railway), not a static-file server
```

There is no test suite. `.env` is **committed** (it only holds `VITE_API_BASE_URL`, the public production backend URL — no secrets), so a fresh clone points at production out of the box. To target a local backend, create `.env.local` (gitignored) with `VITE_API_BASE_URL=http://localhost:8080/api/v1`. If `VITE_API_BASE_URL` is unset entirely, `src/config/api.js` falls back to `http://localhost:8080/api/v1`. Vite reads env files only at dev-server startup — restart after changing them.

## What this project is

Public website for Fitlán Academy: a marketing landing plus a logged-in user area (training feed, training detail, workout steps with video, coach profiles, account/settings). React 19 + Vite SPA, `react-router-dom` v7, Bootstrap 5 (CSS + JS — but JS used sparingly, see Conventions).

This is a sibling of a React Native/Expo mobile app (`rn-starter`, referenced as `../src`). Both hit the **same backend with the same API contract**. The web app is the only place a user can **register a new account and reset a password**; the mobile app is login-only. Differences from mobile: token stored in `localStorage` (not `expo-secure-store`), routing via react-router (not React Navigation).

The full backend API contract is documented in `documentacion-backend/README.md` (2300+ lines) with a Postman collection alongside it. Consult it before touching any service.

## Architecture

**API layer — `src/services/*.js`.** Nearly 1:1 ports of the mobile app's `../src/services/`. Each service is a thin object wrapping endpoint calls. The only file that meaningfully differs from mobile is `services/api.js`.

`services/api.js` is the single choke point: one `request()` helper that injects `Authorization: Bearer <token>`, parses the response, and on **401 with an active token** clears the token and hard-redirects to `/login` unless already there (mobile resets a nav stack instead). It exports `api.get/post/put/patch/delete` plus `setToken/clearToken/getToken`. The in-memory `_token` is seeded from `localStorage` at module load. Errors are thrown as plain objects `{ status, ...body }`, not `Error` instances.

Signature quirk: `get/post/put` take `(endpoint, body?, options?)` and JSON-stringify the body, but `patch(endpoint, options)` and `delete(endpoint, options)` take **only fetch options** — no body argument, no serialization. A PATCH with a payload must pass `{ body: JSON.stringify(...) }` explicitly.

**Auth — `context/AuthContext.jsx` + `services/authService.js` + `components/ProtectedRoute.jsx`.**
- `authService` persists three `localStorage` keys on login: `fitlan_token`, `fitlan_roles`, `fitlan_user_id`.
- `authService.logout()` is deliberately **synchronous and fire-and-forget**: it dispatches `POST /auth/logout` without awaiting (headers are built with the still-valid token at call time), then immediately clears local storage. Do not add `await` here — the subsequent full-page reload would otherwise run with the stale token still present.
- `AuthContext.logout()` does `window.location.href = "/"` (a real reload, not `navigate()`) and intentionally does **not** call `setIsAuthenticated(false)` — that would make `ProtectedRoute` flash `/login` before the browser processes the reload.
- `ProtectedRoute` redirects to `/login` purely off `isAuthenticated` from context. `SubscriptionRoute` additionally requires an active subscription: `AuthContext` fetches `/subscriptions/me` once when authenticated and exposes `hasSubscription` (`null` while loading → shows a Header/Footer "Cargando…" shell; `false` → `<Navigate to="/planes">`). Content routes (`/entrenamientos`, `/entrenamiento/*`, `/entrenador/:id`, `/progreso`) use `SubscriptionRoute`; `/cuenta`, `/configuracion`, `/planes` stay `ProtectedRoute` (session only). `services/api.js` sends `X-Fitlan-Client: web` on every request; the backend uses it to **skip the login-time subscription check for the web client only** (mobile still `401`s a subscription-less login) — see `documentacion-backend/README.md` "Login" → "Excepción para el website". So subscription-less users can log into the web and get routed to `/planes` by `SubscriptionRoute`.
- Registration leaves the account `active=false` until email verification; the backend returns no token, so the user must log in after verifying.

**Routing — `src/App.jsx`.** All routes are declared here in one `<Routes>`. Paths are in Spanish (`/registro`, `/entrenamientos`, `/entrenamiento/:id`, `/entrenamiento/:trainingId/sesion/:sessionId`, `/entrenador/:id`, `/configuracion`, etc.). Public: `/`, `/login`, `/registro`, `/verificar-email`, `/olvide-password`, `/restablecer-password`, `/faqs`, `/privacidad`, `/acerca-de`, `/ayuda`, `/open` (deep-link-with-web-fallback for transactional emails, `?target=training&id=42` — see `OpenLink.jsx`; the backend points `{{COURSE_URL}}` at this instead of `/entrenamiento/{id}` directly, and this attempts `fitlan://training/{id}` before falling back). `/cuenta`, `/configuracion`, `/planes`, `/suscripcion/exito` (Stripe's `success-url`, see below) are `<ProtectedRoute>` (session only); `/entrenamientos`, `/progreso` and the training/coach detail routes are `<SubscriptionRoute>` (session + subscription). A trailing `<Route path="*">` renders `NotFound` (`src/pages/NotFound.jsx`).

**Pages — `src/pages/`, one component per route.** Data fetching is done directly in `useEffect` with `.then/.catch`, errors logged via `console.log`, local `loading` state. No data-fetching library, no global store beyond `AuthContext`.

**Static content pages** (`Privacy`, `Help`, `Faqs`, `About`) pull their body from the backend CMS via `contentService` (`GET /content/*`, public, no token).

**`server.js` — production server, not a plain static-file host.** `npm start` runs it instead of `serve -s dist`. It exists for one reason: `/entrenamiento-publico/:id` (`PublicTraining.jsx`) needs per-training Open Graph/Twitter meta tags when someone shares a training link, but link-preview bots (`facebookexternalhit`, `Twitterbot`, `WhatsApp`, …) don't execute JS, so React setting `document.title` isn't enough. `server.js` detects those bots by `User-Agent` on that one route, fetches `GET /public/training/{id}` server-side, and returns `dist/index.html` with the `og:*`/`twitter:*` tags swapped for the training's own title/description/image (landscape preferred over portrait — standard ~1.91:1 OG aspect ratio) before sending it. Every other request (including that same route for a real browser) gets the normal static file + SPA-fallback behavior `serve` used to provide. The `/public/training/{id}` endpoint is a **backend proposal, not yet implemented** — see `documentacion-backend/PROPUESTA-training-publico.md`; until it exists, the bot branch silently falls through to the generic `index.html` and `PublicTraining.jsx` shows its "not available" state. `TrainingDetail`/`Steps`/`StepPlayer`'s share buttons already point at this public URL (`${origin}/entrenamiento-publico/{trainingId}`), not `window.location.href` — a shared link has to work for someone with no session.

**Training → session → step navigation adapts to the training's shape.** `GET /training/{id}` returns `sessions[]` each with `steps[]` embedded, and `TrainingDetail` branches on that after load: **1 session / 1 step** → `<Navigate replace>` straight to the step player `/entrenamiento/:tid/sesion/:sid/step/:stepId`; **1 session / 2+ steps** → `<Navigate replace>` to the session's step list (`Steps`); **2+ sessions** → stay on `TrainingDetail` showing the session list, where each row links straight to the step player if that session has 1 step, otherwise to its step list. `Steps` renders the step list with the same `.sessions-list` styling as the session list; each row links to `StepPlayer`. `StepPlayer` (`src/pages/StepPlayer.jsx`) mirrors the session-page layout (`Header`/hero/`training-meta`/description + `Footer`) — it loads both the session and the training (for coach + title + description) and shows share / "Entrena con {coach}" / follow / duration. In the hero, in place of the image, sits the step `<video>` (`.training-hero-video`, native `controls` once playing, custom timer pill + play button + title overlay while paused). It registers `enrollmentService.completeSession` on entering each step. Both `Steps` and `StepPlayer` render a `Breadcrumb` (`src/components/Breadcrumb.jsx`) — training → session (→ step) — for orientation and back-navigation (no dedicated back button). `Breadcrumb` uses a `<div role="navigation">`, not `<nav>`, because the mockup's global `nav {}` rule absolutely-positions any `<nav>` as the mobile menu.

## Conventions specific to this repo

- **This is a port of static mockups** in `../maquetas` (HTML/PHP + Bootstrap). Most components/pages carry a header comment naming the mockup file they came from and what changed. When the mockup had hardcoded data the backend doesn't provide (e.g. star ratings on training cards), the port **omits it rather than faking data** — keep this principle.
- **Bootstrap JS is imported in `main.jsx` (`import 'bootstrap'`), but use it sparingly.** The only component driven by it is the Landing info carousel (`Carousel` instantiated in a `useEffect` + `dispose()` on unmount, since `data-bs-ride` auto-init doesn't catch React-rendered DOM). For interactive widgets React re-renders, still reimplement with React state (e.g. the Header menu) — mixing Bootstrap's imperative DOM writes with React's virtual DOM causes desync. Rule of thumb: only reach for a Bootstrap JS component when its subtree is static after mount.
- **CSS**: `src/assets/css/styles.css` is the original mockup stylesheet, copied verbatim — avoid editing it. New-screen styles (login, register, settings, my-trainings, plans, FAQs) go in `src/assets/css/app-extra.css`. Both are imported in `main.jsx` after `bootstrap.min.css`.
- **Subscription checkout is real, via Stripe.** `POST /subscriptions/checkout` (`{ plan }`) and `POST /subscriptions/portal` both return `{ url }` — a Stripe-hosted page (Checkout / Customer Portal) to redirect to with `window.location.assign`, never an embedded card form, so no payment data touches this app. The backend de-dupes `checkout` server-side using the **same criterion as `GET /subscriptions/me`** (confirmed by testing after an earlier version checked `stripe_customer_id` presence instead, which kept returning the portal even for users with zero active subscriptions — a stale `stripe_customer_id` never gets cleared by cancellation): if `/me` 404s, `checkout` always creates a fresh Stripe session; otherwise it returns the **portal** URL instead of a second checkout. So `Plans.jsx` never shows "Adquirir" buttons to an already-subscribed user (would silently open the portal instead, which is confusing), it shows only the current plan + one "Gestionar suscripción" button; the 3-plan grid with per-plan "Adquirir" only renders when `/me` 404s. `Account.jsx` mirrors that same current-plan/status view with its own "Gestionar suscripción" — deliberately not a "Cambiar de plan" link to `/planes`, which would just show the identical thing. `subscriptionStatusMeta()` (`subscriptionService.js`) maps status to a label + color (green ACTIVE, blue TRIALING, orange PAST_DUE) shared by both pages — checked before that: `cancel_at_period_end: true` (set by a normal Customer Portal cancellation, which does **not** change `status`) or literal `status === "CANCELED"` both render identically as "Cancela el {fecha}" in gray, since what the user needs to know is the same either way. Checkout/portal calls can 400 (plan without `stripe_price_id` configured; portal — or checkout — without a `stripe_customer_id`). That last one also covers subscriptions an admin assigned manually from the CMS: those still get a 200 from `/me` (frontend can't tell them apart from a Stripe one, the response doesn't expose `stripe_customer_id`), so "Gestionar suscripción" still renders for them, but clicking it 400s — `isManualSubscriptionError()` matches that exact backend message to swap in a "contact us" message instead of the generic retry copy, since retrying changes nothing there. Stripe's backend-configured `success-url` is `/suscripcion/exito` (`SubscriptionSuccess.jsx`, confirmed by testing); `cancel-url` is plain `/planes` (no dedicated page needed — canceling has nothing to confirm, unlike success). `SubscriptionSuccess.jsx` reads Stripe's `?session_id=cs_...` and calls `GET /subscriptions/sync/{sessionId}` — a fallback that activates the subscription immediately instead of waiting on the webhook (which still runs, and is still what handles renewals/cancellations/failed payments after the fact); a failed sync call doesn't block the page, the webhook catches it eventually. Unrelated: the mockup's "Solicitar entrenamiento personalizado" button was removed from `TrainingDetail` — no backend endpoint for that, still routes to email contact via `Help.jsx`.
- `subscriptionService.getMySubscription()` returns **404 when the user has no subscription** — that is not an error, handle it explicitly in callers. `ACTIVE_SUBSCRIPTION_STATUSES` / `hasSubscriptionAccess()` in that file define which statuses still grant content access.
- `trainingService.getTrainings()` returns a plain array normally, but a paginated `{ items, page, page_size, total_items, total_pages }` object when a `page` arg is passed.
- **`country`/`state`/`city` location fields**, added across several user-facing endpoints, are plain text names (not ISO codes) — `POST /auth/register` (optional, persisted before the account is even active — there's no later chance to set them, since a fresh registration has no valid token until email verification + login), `GET/PUT /users/me` (the only self-service edit endpoint on the whole site — `userService.updateMe()`), and `GET /users/coaches[/​{id}]` (country + city only, no state). `LocationSelect.jsx` is the shared cascading País→Estado→Ciudad picker (`Register.jsx`, and `Account.jsx`'s inline "Editar" on the location line) built on the `country-state-city` npm package — same one the admin CMS panel uses. That package's dataset is ~9MB; `LocationSelect` dynamically `import()`s it inside a `useEffect` instead of a static top-level import, so Vite code-splits it into its own chunk that only downloads when someone actually opens Register or the location editor, not on every page load (a static import bloated the main bundle from ~500KB to ~9MB). Since the backend stores names, not codes, `LocationSelect` resolves each select's `isoCode` by looking up the current name in that same render's dataset (`Country.getAllCountries().find(c => c.name === value)`), never from free text, so it stays consistent. `CoachProfile.jsx` shows `[city, country].filter(Boolean).join(", ")` read-only (replaced the old dev-only `location` placeholder); `Account.jsx` shows all three joined the same way, editable inline.
- **`motto`** (max 160 chars, `GET/PUT /users/me` and the coach endpoints) is coach-only — `CoachProfile.jsx`'s banner quote (replaced the old fake `quote`/`quote_author` placeholders; genuinely optional, so the quote `<figure>` just doesn't render without one, though the gradient `coach-hero` banner strip itself still does), read-only there since that page is for viewing *other* coaches. It's edited on `Account.jsx` instead (own profile) — same inline "Editar" pattern as `description`/`name`/location, but gated behind `user.roles.includes("ROLE_COACH")` since a plain user has nothing to put there.
- **Coach certifications** — a separate resource, not a field on the user object: `GET/POST /users/me/certifications` + `DELETE /users/me/certifications/{certId}` (COACH, ADMIN self-service; `userService.getMyCertifications/addCertification/deleteCertification`), each `{ id, name }` (`name` max 200 chars). `GET /users/coaches[/​{id}]` embeds the same shape as `coach.certifications`. `CoachProfile.jsx`'s "Diplomados o Certificaciones" aside section reads that array read-only (it used to render the fake `PLACEHOLDERS.languages` — real data replaced it directly, no other placeholder for this section exists). `Account.jsx` gets full CRUD on the same section, `isCoach`-gated like `motto`: chips get a small "×" (`.account-chip-remove`) to delete, plus an "+ Agregar certificación" trigger reusing the `.account-edit-trigger`/`.account-description-edit` inline-form pattern. Fetched in its own `useEffect` keyed on `isCoach` (not the initial profile-load effect) since the endpoint 403s for a non-coach and `isCoach` isn't known until `GET /users/me` resolves.
- **`coach.trainings`** in `GET /users/coaches[/​{id}]` embeds the *full* training shape (same as `GET /training/{id}`: `categories`, `image_url`/`image_landscape_url`(+keys), `difficulty_level`, `sessions[].steps[]`, etc.) — it briefly returned only `{ id, title }`, which forced `CoachProfile.jsx` into an N+1 workaround (one `getTrainingById()` per training) just to render `TrainingCard` correctly and to derive "Disciplinas destacadas"; that workaround was requested-and-fixed backend-side and has been removed, `coach.trainings` is read directly again. **"Disciplinas destacadas"** = the categories of the trainings that coach teaches, not a field the backend sends directly — `disciplineCategories` in `CoachProfile.jsx` is `coach.trainings.flatMap(t => t.categories ?? [])` deduped by `id` via a `Map` (several trainings can share a category). `PLACEHOLDERS.disciplines` is gone — the last fake field on that page besides `role` (still backend-less, unrelated to categories).
- **`Account.jsx` editable fields — `name`, `description`, `motto`, `country`/`state`/`city`, `profile_image_url`, `instagram_url`/`facebook_url`/`tiktok_url`** — all via the same inline "Editar" trigger (`.account-edit-trigger`) swapping to a small form + Guardar/Cancelar (the photo instead shows a camera-icon overlay, `.account-photo-edit`, since there's nothing to "start editing" — picking a file both uploads and saves immediately; social links are one "Editar" covering all three URLs at once, like location). All of it goes through `userService.updateMe()` (`PUT /users/me`). The footgun this depends on: `country`/`state`/`city`/`profile_image_url`/`instagram_url`/`facebook_url`/`tiktok_url` are **not** like the endpoint's other fields — leaving any of them out of the body is treated the same as sending `null`, i.e. they get cleared, not left alone (documented in the README, "Actualizar perfil propio"). `currentProtectedFieldsPayload()` reads the current value of all seven from `user` and gets spread into *every* save on this page, the field(s) actually being edited then overriding their entry — so saving the name doesn't wipe the location, saving the location doesn't wipe the photo or social links, etc. (`profile_image_url` there is `user.profile_image_key`, the raw key — the field name is `*_url` but the write-value is a key, not the signed URL `GET` returns under that same name). This was originally only built for `country`/`state`/`city` (a real bug: saving the description used to clear the location) — widening it to cover the photo/social fields too, when the social-link editor was added, fixed the same class of bug for those before anyone hit it live. `name` additionally validates non-empty client-side (unlike the others, an empty name isn't a valid "clear it" state). `instagram_url`/`facebook_url`/`tiktok_url` are `isCoach`-gated (same as `motto`/certifications) and read-only on `CoachProfile.jsx`'s "Sígueme en:" (viewing other coaches).
- **File uploads — `services/fileService.js` + `api.upload()`** (new, first use of this pattern in the repo). `POST /files/upload` (`multipart/form-data`, field name `file`) returns `{ key, url }`; per the README's "Archivos (S3)" section, the `key` (not the signed `url`) is what gets sent back in the resource's own `*_url`-named field on write (e.g. `profile_image_url` — the field's write-value and read-value have different shapes: a raw key going in, a freshly-signed URL coming back out). `api.js`'s `request()` only skips its default `Content-Type: application/json` when `options.body instanceof FormData`, so the browser can set its own `multipart/form-data; boundary=...` — every other call path is unaffected. Before uploading an image, run it through `utils/imageCompress.js`'s `toCompressedJpeg(file)` — camera photos land several MB and sometimes PNG; it decodes via `createImageBitmap`, downscales to a 1280px longest side, flattens onto a white `<canvas>` background (JPEG has no alpha channel — without this a transparent PNG turns black) and re-encodes as JPEG at 0.85 quality, renaming to `.jpg`. Falls back to the original `file` untouched if decoding throws (e.g. an unsupported format), so a compression failure never blocks the upload. Currently only wired into `Account.jsx`'s profile-photo upload; reuse it for any future image-upload flow rather than uploading the raw `<input type="file">` value.
- **`description`** is a real field on `/users/me` (not a placeholder) — `Account.jsx` had been reading a fake dev-only `user.bio` instead and silently showing nothing in production; fixed to read `user.description`, same field `CoachProfile.jsx`'s "Experiencia" section already used correctly (read-only there — coaches don't self-edit their profile from the website). On `Account.jsx` it's editable inline via the same "Editar" trigger pattern as the location fields (`account-edit-trigger`, shared by both) — a `<textarea>` + Guardar/Cancelar swapped in, `PUT /users/me` with `{ description: value || null }`.
- Some services (`notificationService` device-token registration, Facebook login in the backend docs) are ports carried over from mobile and may not be wired into any web page.
- **S3 image/video URLs are re-signed on every request** (`image_url` etc. carry a fresh `X-Amz-Date`/signature each time; the objects send no `Cache-Control`), so the same asset re-downloads on every navigation. `src/utils/assetUrl.js` (`assetUrl(url, key)`) memoizes the first signed URL seen per permanent `*_key` (`image_key`, `profile_image_key`, `video_key`, …) and returns it for the rest of the session, keeping `<img>`/`<video>` `src` byte-stable so the browser's in-session cache serves repeats. **Always wrap S3 asset URLs with `assetUrl` in new `<img>`/`<video>`.** Persistent (cross-reload) caching still needs the backend to set `Cache-Control` on the objects.
- **Shared helpers live in `src/utils/`** — `format.js` (`formatDifficulty` / `difficultyLabels` → "Nivel Básico" etc.; `formatDifficultyShort` → "Principiante/Medio/Avanzado", used on feed cards; `firstName`; `formatDuration` seconds→`"N min"`), `initials.js` (`getInitials`), `assetUrl.js` (`assetUrl` — see the S3 note below). Reuse these rather than re-deriving label maps or name parsing per page.
- Icons come from **`react-icons`** (e.g. `react-icons/io5`); there is no local icon component set.
- `oxlint` config is `.oxlintrc.json`: `react/rules-of-hooks` is an error, `react/only-export-components` a warning (constant exports allowed). `npm run preview` needs a prior `npm run build`.
